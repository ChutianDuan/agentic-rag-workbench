# 本地小模型路由与双模型 RAG 优化路线图

## 1. 目标与判断

下一阶段的主线调整为：

**本地小模型判断需求 → 按需检索知识库 → 选择小模型或远端强模型回答 → 用评测验证收益。**

这个方向适合当前项目。它可以减少不必要的检索和强模型调用，但每次请求会增加路由开销，错误路由也可能损害答案质量。因此，采用“质量优先、成本收益通过实验确认”的策略。[RouteLLM](https://arxiv.org/abs/2406.18665) 和 [Adaptive-RAG](https://arxiv.org/abs/2403.14403) 分别提供了模型选择和按需检索的研究参考，论文收益不直接作为本项目承诺。

当前项目已有异步入库、LanceDB 检索、rerank、引用持久化、Agent Trace、SSE 断线续传和模型 API 接入。现有模型调用使用一套配置，普通 Chat 固定先检索，Agent 另有关键词检索判断。第一版在这些能力上接入双模型与四路路由，覆盖现有 Agent 的普通与 SSE 入口；普通 RAG Chat 保留现有行为。

> 历史测试记录：旧路线图记录过 `125 passed, 3 skipped`，并将检索对比、chunking recall 和 reranker 相关跳过归因于当时的 NumPy/FAISS 环境缺失。本次仅更新文档，未重跑测试；该数字不代表当前基线，需在 P0 重新验证。

## 2. 四路架构与执行规则

“是否需要知识库”和“需要哪个模型”是两个独立决策。复杂文档问题可以同时使用 RAG 和强模型 API。

| 路径 | 适用问题 | 执行方式 |
| --- | --- | --- |
| 小模型直答 | 问候、简单解释、轻量改写 | 本地小模型回答 |
| RAG＋小模型 | 文档内单点事实、简单信息提取 | 检索、重排后交给小模型 |
| 强模型直答 | 不依赖知识库的复杂推理、代码分析 | 调用远端强模型 API |
| RAG＋强模型 | 跨文档综合、基于项目资料的复杂分析 | 检索、重排后交给强模型 |

- 每个新请求只做一次前置路由，输入包含问题、已有会话摘要和最近对话。需要检索时，同次输出补全指代后的检索问题。
- 小模型使用短提示词输出结构化决策，不生成长推理过程；路由请求关闭现有自动续写机制。
- 用户明确要求依据知识库或上传文档回答时，必须检索；通用技术术语本身不再直接触发强制检索。
- 路由无法判断时选择强模型；涉及文档上下文的歧义同时保留检索。指代无法解析时请求澄清。
- 检索为空或证据不足时明确说明限制。强模型用于提高理解与推理能力，不能代替缺失证据。
- 保留现有文档详情、文档列表、历史引用工具。四路选择控制知识检索与回答模型，不删除这些能力。

## 3. 分阶段实施

以下阶段均为后续实施任务，本次文档更新不表示这些能力已经完成。

### P0：双模型接入与对照基线

- 在[现有模型调用模块](../python_rag/app/modules/llm/service.py)增加按请求选择模型配置的能力，复用 HTTP、响应解析和异常处理，不复制两套客户端，不动态修改全局配置。
- 新增独立的小模型配置；现有 `LLM_*` 保留为远端回答模型及兼容默认配置。本地同一个模型服务承担路由和轻量回答。
- 路由请求单独限制超时、输出长度和生成轮数；普通生成及工具调用继续使用相应模型的配置。
- 使用现有 vLLM 启动能力接入本地模型，验证结构化输出、普通生成和现有工具协议。型号与服务商作为部署配置，不写死。
- 冻结语料、问题集、检索参数与提示词，记录当前 Agent 在固定远端模型下的质量和调用成本。
- 重新验证测试基线，检查历史 skip 原因，确保质量关键测试没有意外跳过。记录测试命令、依赖环境和 Git commit，再更新当前测试结果。

### P1：接入四路路由

- 在[现有意图路由模块](../python_rag/app/agent/intent_router.py)定义内部 `RouteDecision`，包含是否检索、回答模型、检索问题、简短原因和不确定标记。
- Agent 创建 Trace 后调用路由器，随后使用选定模型执行现有回答及工具流程；路由步骤不占用原有工具步数预算。
- RAG 路径先执行知识检索；非 RAG 路径不开放 `knowledge_search`，其他只读工具继续按现有权限工作。
- 保留原关键词判断作为路由异常时的降级依据，并结合会话中的文档上下文；正常请求以新决策及明确文档约束为准。
- 路由超时或响应非法时，直接降级到远端模型，不循环修复 JSON。小模型生成失败时，允许携带已有证据向强模型升级一次；强模型失败返回明确错误。
- 增加一个默认关闭的路由开关，关闭时恢复原 Agent 路径，便于对照和回退。

### P2：可观测性与评测闭环

- 通过已有 Trace、消息 metadata 和指标扩展字段记录：初始路线、实际回答模型、降级原因、检索调用、分模型 token、路由耗时及总耗时。
- API 费用与本地推理耗时、GPU 占用分别报告；没有价格或 usage 时标为未知或估算，不能将本地运行视为零成本。
- HTTP 请求结构和 `{code, message, data}` 保持兼容；路由信息通过已有 Trace 和可选 metadata 暴露，不新增业务端点或数据库表。
- SSE 保持递增事件 ID，每条事件数据包含 `type`，并以 `done` 或 `error` 结束；断线后继续生成，按 `Last-Event-ID` 续传，过期恢复报错。最终消息与引用持久化后再发送 `done`，恢复连接不重新路由或生成。
- 建立离线批量评测 runner，一条命令生成可版本化的 JSON 和 Markdown 报告。保存模型版本、路由提示词版本、切片配置、top-k、reranker、费用口径和 Git commit，支持与历史 baseline 比较。

### P3：由失败样本推动后续优化

保留原路线图中的以下方向，排在四路方案评测之后，按失败样本确定优先级：

| 方向 | 后续任务 |
| --- | --- |
| 引用验证 | 区分检索候选来源与答案实际使用的引用，校验引用是否支持对应结论 |
| 来源定位 | 保留标题路径、PDF 页码、表格位置、来源 URL 和字符范围，改善证据定位 |
| 混合检索 | 对精确词召回失败样本比较 dense、BM25、RRF 与 rerank，并独立比较 query rewrite 和切片参数 |
| 工程可靠性 | 补 Gateway 合约测试，在独立环境做可复现的 LanceDB 备份恢复与 embedding 切换重建演练 |

先区分路由错误、解析丢失、召回失败、重排失败、生成幻觉和引用错误，再决定具体修改。不同时引入路由微调、新工具或向量数据库替换。

## 4. 测试与验收

### 评测数据

- 首版整理约 100 条自有问题，覆盖四路、多轮指代、文档无答案、工具请求和易误判的通用技术问题。
- 按会话和近似问题分组，划分开发集与固定测试集，避免同类改写泄漏；提示词调整使用开发集，固定测试集用于验收。
- 保留答案要点、是否必须检索和稳定证据锚点。证据使用 `doc_key + evidence_text` 定位，入库后再解析为实际 chunk，避免依赖重建后会变化的数据库 ID。
- 模型选择标签参考小模型与强模型的实际回答结果，不仅凭问题长短判断。人工参考答案与证据是验收依据，不能仅依赖模型自报置信度。

### 对照实验

在相同语料、检索配置和模型组合下比较：

1. 原关键词路由＋统一远端模型。
2. 小模型判断是否检索＋统一远端模型。
3. 小模型四路路由。

报告回答正确率、引用支持率、无答案拒答表现、漏检索率、强模型调用比例、token 与费用、路由及端到端延迟。统计实际模型调用，包括路由、工具决策、续写和失败升级带来的额外调用。

首版沿用 Agent 当前完整答案生成后发送 `delta` 的行为，不把该事件时间标成模型真实首 token 延迟。确定性回归使用 mock，不依赖真实付费 API；真实模型对照在单独的评测阶段运行。

### 自动化回归

- 四条路径实际调用正确，路由每次只执行一次，路由请求不会触发自动续写。
- 文档问题不会绕过检索，普通技术问题不会仅因关键词被强制检索；多轮指代与无法解析时的澄清符合约定。
- 非法 JSON、路由超时、小模型失败、强模型失败和空检索按约定处理，不循环升级，不用无证据回答掩盖失败。
- 双模型并发请求的配置不串用，既有工具能力和调用预算保持有效。
- API envelope、SSE 续传、过期状态、持久化顺序及旧 Chat 路径通过回归；续传不重复产生路由或模型调用。
- 关闭路由开关后恢复原 Agent 行为，便于与基线比较。

### 默认启用门槛

固定测试集上的回答正确率、引用支持率和拒答表现均不低于统一远端模型基线，必须检索样本无新增漏检；同时强模型调用量与实测 API 费用下降。没有可核实的费用数据时，不认定费用门槛已经达成。

未达到门槛时保持开关关闭，通过开发集和失败样本调整策略，再按固定口径验收，不宣称优化已经成立。

## 5. 已确认的假设与边界

- 本地小模型兼任路由器和简单问题回答模型；远端 API 提供更强的生成能力。
- 采用四路选择，质量优先，首版仅改造 Agent。
- 暂不锁定具体型号和服务商；每轮比较固定模型组合与版本。
- “API”指强模型推理接口，本阶段不增加业务 API 工具或联网搜索。
- 首版使用提示词路由，不训练路由模型；模型下载、部署和真实 API 评测在后续实施阶段进行。
- 本轮产出为路线图文档，不修改代码、敏感配置或现有数据；P0 至 P3 的实现与评测结果另行记录。
